# 零停机切换深度分析

## 问题定义

目标：将 suggest 从 `*wildcard*` 切换为 `ngram match`。

涉及的组件：
- **`EsIndexConfig.getMaterialSearchIndexName()`** — suggest 和 sync 共用索引名
- **`MaterialSuggestService`** — 查询代码
- **`MaterialSearchSyncServiceImpl`** — 增量写入代码
- **`MaterialSearchReindexTask`** — QSchedule 全量重建

---

## 零停机方案汇总（与停机方案放在一起对比用）

### 方案 A：Boolean Flag 控制

核心思路：加一个布尔开关，`flag=false → wildcard`，`flag=true → ngram`。1 次部署，2 个 hotfile key 同批原子切换。

| 优点 | 缺点 |
|------|------|
| 1 次部署 | 多一个布尔开关 |
| 无停机窗口 | 两个 key 必须同时变更 |
| 回滚简单 | |

> 见上方详细方案 A 分析。

### 方案 B：两阶段部署

核心思路：第一阶段只部署基础设施（不含 suggest 改动）→ reindex → 切索引名 → 第二阶段部署 suggest ngram 代码。

| 优点 | 缺点 |
|------|------|
| 无需布尔开关 | 需要 2 次部署 |
| 每阶段都安全 | 部署间隔增加风险 |
| Stage 1 切完后 suggest 仍工作 | |

> 见上方详细方案 B 分析。

---

## 可接受停机 → 3 个简化方案

如果接受停机，可以大幅简化：**去掉 side index、去掉 Boolean flag、去掉双索引切换**。

### 方案 D（推荐）：原地 close/reopen，同索引名

#### 原理

不建新索引，直接在现有索引上操作：close → 更新 settings（加 ngram analyzer）→ open → putMapping（加 ngram 子字段）→ 全量 reindex。**索引名不变**，代码里不需要任何配置切换。

#### 操作步骤

```
                         停机窗口开始
                              │
  部署代码（suggest ngram + reindex 任务）
                              │
   Step 1: 关闭旧索引  POST _close            ~1-2s
   Step 2: 更新 settings（加 ngram analyzer）   ~100ms
   Step 3: 打开旧索引  POST _open             ~1-2s
   Step 4: putMapping（加 material_label_common_tag.fields.ngram）
                              │
                         停机窗口结束（总耗时 ~3-5s）
                              │
   Step 5: 触发 QSchedule reindex 任务
          （从 MySQL 全量读取 → assemble → upsert，存量数据重新走 mapping 后 ngram 才会生效）
                              │
   suggest 用 ngram 查同索引 → 正常工作 ✅
   sync 写入同索引 → 正常工作 ✅
```

#### 代码改动

新增的 API：
- `ElasticsearchDataSource.closeIndex(index)` — `CloseIndexRequest`
- `ElasticsearchDataSource.openIndex(index)` — `OpenIndexRequest`
- `ElasticsearchDataSource.putMapping(index, mapping)` — `PutMappingRequest`

整个流程封装到 `MaterialSearchReindexTask` 的 `doReindex()` 中，按顺序执行 close → settings → open → mapping → MySQL sync。

#### 优缺点

| 优点 | 缺点 |
|------|------|
| **最简单**：没有 side index，没有 Boolean flag，没有索引名切换 | 需要 ES 集群支持 close/open（某些云 ES 不允许 close） |
| 索引名不变：`EsIndexConfig` 完全不用改 | 停机窗口 ~3-5 秒 |
| `MaterialSuggestService`：直接用 `.ngram` 查，不需要 if-else | 需要新增 3 个 ES API（close/open/putMapping） |
| `sync()` 完全不用改 | close 期间写入请求会报错（建议先停写入或容忍短暂失败） |
| 回滚：只能重建旧索引（需从 MySQL 全量恢复） | |
| 不需要 `syncToIndex` 接口 | |

### 方案 E（最简单粗暴）：删索引重建

#### 原理

直接 `DELETE 旧索引` → `CREATE 新索引（含 ngram mapping）` → QSchedule 全量同步。

```
                         停机窗口开始
                              │
   DELETE odin_material_search        ~100ms
   CREATE odin_material_search（含 ngram）~500ms
                              │
                         停机窗口结束（~1s，但索引是空的）
                              │
   触发 QSchedule reindex（从 MySQL 全量同步）
          → 数据逐步恢复，但恢复期间 suggest 查不到新数据
                              │
   reindex 完成 → suggest 正常工作 ✅
```

#### 关键问题

reindex 是耗时的（几分钟），从**索引重建完成到 reindex 结束**这段时间：
- suggest 能查到数据但不全（部分 reindex 进度）
- sync 写入能工作（upsert）

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 代码改动最少：只需 ElasticsearchDataSource 加 `deleteIndex` | 间歇期（reindex 未完成时）suggest 数据不完整 |
| `EsIndexConfig` 完全不用改 | 回滚需要重建旧索引并全量同步 |
| `MaterialSuggestService` 直接用 `.ngram` | |
| `sync()` 完全不用改 | |

### 方案 F：ES Alias 原子切换

#### 原理

在现有索引上创建 alias（如 `odin_material_search_alias`），之后所有代码指向 alias 而非具体索引名。建 v2 索引 → reindex 完成 → alias 原子切换 → 旧索引删除。切换耗时 ~100ms。

```
  EsIndexConfig 改为指向 alias
  Code → odin_material_search_alias → (指向 旧索引)

  Step 1: 创建 odin_material_search_v2（含 ngram mapping）
  Step 2: 全量 reindex 到 v2（此时 alias 仍指向旧索引，正常运行）
  
                          停机窗口开始（~100ms）
  Step 3: 原子切换 alias：
          PUT _aliases
          { "actions": [
              { "remove": { "index": "odin_material_search", "alias": "odin_material_search_alias" } },
              { "add":    { "index": "odin_material_search_v2", "alias": "odin_material_search_alias" } }
          ]}
                          停机窗口结束

  Step 4: 删除旧索引 odin_material_search（可选）
```

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 停机窗口极短（~100ms） | EsIndexConfig 需改为指向 alias（一次部署改动） |
| suggest + sync 都指向 alias，切换后自动对新索引起效 | ElasticsearchDataSource 需加 `updateAliases` 方法 |
| reindex 期间对旧索引无影响 | 一次部署完成（alias 是静态配置，无需热配） |
| 回滚：alias 切回旧索引即可 | |

## 全部方案对比总结

| 维度 | A. Boolean Flag | B. 两阶段部署 | D. close/reopen | E. 删重建 | F. Alias 切换 |
|------|:---:|:---:|:---:|:---:|:---:|
| **停机时间** | 0 | 0 | ~3-5s | ~1s* | ~100ms |
| **部署次数** | 1 | 2 | 1 | 1 | 1 |
| **代码改动量** | 中 | 中 | 中 | 少 | 中 |
| **EsIndexConfig 改动** | 需要 | 需要 | 不需要 | 不需要 | 需要（指向 alias） |
| **新增 ES API** | deleteIndex | deleteIndex | close/open/putMapping | deleteIndex | updateAliases |
| **Boolean flag** | 需要 | 不需要 | 不需要 | 不需要 | 不需要 |
| **Side index** | 需要 | 需要 | 不需要 | 不需要 | 需要 |
| **数据完整间歇期** | 无 | 无 | 无 | 有 | 无 |
| **操作复杂度** | 中 | 高 | 低 | 最低 | 中 |
| **回滚难度** | 低（删 key） | 低（切配置） | 高（需重建索引） | 高 | 低（切 alias） |

> *E 方案索引重建 ~1s，但 reindex 期间数据不完整（间歇期），严格说停机 + 同步时间 = 分钟级不可用。

## 我推荐

如果**接受停机**，**方案 D（close/reopen）** 最优：
- 3-5 秒停机能接受的投资回报率最高
- 不需要 side index、不需要 Boolean flag、不需要双索引切换
- 索引名不变，`sync()` 不用改
- 操作步骤最少

如果**不能接受 3-5 秒停机但能接受 100ms**，**方案 F（Alias）** 最优：
- reindex 期间对线上无影响
- 切换近乎瞬时
- 回滚简单
